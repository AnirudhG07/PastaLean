# PastaBench

A verification benchmark for **Python → Lean 4**: 300 real LeetCode problems shipped with their
Python source, their test cases, the Lean that [PastaLean](../README.md) generates from that
source, and hand-written correctness proofs about it.

The point is not "can we translate Python" — `cp_harness` already measures that over 2589
problems. The point is **can the translated code be reasoned about**: does PastaLean state the
right theorem, hand you usable goals, and how far can a human take them.

---

## Layout

One directory per problem, everything co-located, module path = directory path:

```
PastaBench/leetcode/HouseRobberIii/
    problem.txt      the LeetCode statement
    meta.json        task_id, entry method, params, difficulty, bucket, feature, n_tests
    solution.py      the Python — SOURCE OF TRUTH; contracts/asserts are added here
    tests.json       test cases (input/output), the same ones cp_harness evaluates against
    Generated.lean   AUTOGENERATED by PastaLean — regenerated on demand, DO NOT EDIT
    Proofs.lean      HUMAN-WRITTEN — imports Generated; regeneration never touches it
```

### The two-file rule

**This is the load-bearing convention.** Regenerating the Lean must never destroy a proof
someone spent a day on, so generated output and human output never share a file:

| file | written by | `pastabench.py regen` |
|---|---|---|
| `Generated.lean` | PastaLean | **overwrites it** |
| `Proofs.lean` | a human | never reads or writes it |

`Generated.lean` is wrapped in `namespace PastaBench.leetcode.<Module>` so 300 problems — each
defining its own `main`, `inf`, entry method — coexist in one Lean library. `Proofs.lean` imports
that module and states theorems in the same namespace.

### Keeping a hand-written statement honest

A hand-written proof restates the theorem, which risks drifting from the one PastaLean actually
generated — proving something easier than what was claimed. Close that hole with a one-line
fidelity check; `rfl` typechecks **only if the two statements are definitionally equal** (both
sides are proofs, so `Eq` forces their types to agree, and proof irrelevance closes it):

```lean
theorem rob_spec' : <the generated statement> := by
  <hand-written proof>

example : rob_spec = rob_spec' := rfl   -- ← fails to compile if the statements differ
```

So `lake build PastaBench` fails if a human ever drifts a statement away from the machine's. The
benchmark self-checks.

## The 300

Selected from the 1531 `cp_harness` LeetCode problems whose Lean both **converted and compiled**,
stratified so the bench spans the whole difficulty and language-feature range.

| bucket | n | what it is | provable today |
|---|---|---|---|
| `term` | 100 | compiled to a **bare Lean term** (no `Id.run do`) — recursion, comprehensions, `sum`/`map`/`min` | ✅ directly, via `assert`/contracts + `taste?` |
| `loop` | 200 | compiled to `Id.run do` — `for`, `while`, mutation, classes | via the mvcgen (`for`) and `pyWhile` (`while`) tracks |

`loop` is stratified further by the feature that makes it hard: 100 `while`, 75 `for`-only, 25
class-using. Difficulty across all 300: 93 Easy / 147 Medium / 60 Hard.

Selection is deterministic (`--seed`), prefers well-tested problems, and breaks ties toward
smaller Lean — a benchmark problem is only useful if a human can actually finish its proof.

## The `stdlib/` track

The second half of the benchmark: real Python standard-library **algorithms**, hand-curated
instead of sampled, laid out identically under `PastaBench/stdlib/<Module>/` and namespaced
`PastaBench.stdlib.<Module>`. Same two-file rule.

Where the LeetCode track measures *breadth* (can PastaLean state a goal across 300 varied
programs), this track measures *depth*: take one piece of real Python and prove it fully correct
against its mathematical specification.

**`Gcd` — done, 0 `sorry`.** Euclid's algorithm as pure Python, contracted with
`Invariant`/`Decreases`, transpiled through the verified `while` track (`pyWhile`). PastaLean
proves the Hoare triple its contracts state (`Result() ≥ 0`); `Proofs.lean` then proves the real
theorem — **the transpiled function computes exactly `Int.gcd`**:

```lean
theorem gcd_eq_intGcd (a b : Int) (ha : 0 ≤ a) (hb : 0 ≤ b) :
    Id.run (gcd a b) = (Int.gcd a b : Int)
```

From there, "divides both arguments" and "is the *greatest* common divisor" are one-liners via
Mathlib. `#print axioms` reports only `propext, Classical.choice, Quot.sound`.

### Choosing the next stdlib target

The verified `while` track (`PastaLean/PyVerify/Contracts.lean:363-375`) accepts a loop body of
**straight-line assignments to bare names only** — no `if` inside the body (line 370), no
subscript targets like `h[i] = v` (line 372). So:

- Loop state must be scalar variables; copy parameters into locals first (parameters cannot be
  loop state) and initialise every loop-assigned variable before the loop.
- `a, b = b, a % b` → unroll through a temporary.
- An `if` in the loop body → rewrite as ternary assignments (`lo = mid + 1 if … else lo`).
- Pure Python only: no C accelerator, no `yield` / `with` / `async`.
- Anything doing `heap[i] = heap[j]` inside a loop (CPython's `heapq._siftup`) is **out of reach**
  today — that needs array-valued loop state in the combinator.

Comprehension-shaped code (`statistics.mean`, `variance`) needs no loop track at all: it stays a
bare Lean term and is provable directly.

## Workflow

```bash
# choose the problems and record the selection            (rarely — it defines the benchmark)
python3 PastaBench/pastabench.py select --dataset cp_harness/dataset_leetcode

# create/refresh the per-problem directories from manifest.json
python3 PastaBench/pastabench.py materialize

# re-translate solution.py -> Generated.lean; Proofs.lean untouched
python3 PastaBench/pastabench.py regen --only Gcd
python3 PastaBench/pastabench.py regen                       # both tracks

# how far along are the proofs?
python3 PastaBench/pastabench.py status

# typecheck the whole benchmark (generated code + every proof)
lake build PastaBench
```

`materialize` preserves any `Proofs.lean` that already exists. `--force-proofs` overwrites them
and is the one destructive flag here.

### Adding a proof to a problem

1. Add contracts to `solution.py` — `Requires` / `Ensures` / `Invariant` / `Decreases` /
   `Assert`, from the `passta` shim. What each one means and where to put it:
   [`docs/contract-prompt-system.md`](../docs/contract-prompt-system.md).
2. `pastabench.py regen --only <Module>` — PastaLean lifts the contracts into a Hoare-triple
   theorem in `Generated.lean` and discharges what `taste?` can, leaving `sorry` for the rest.
3. Write the proof in `Proofs.lean`, restating the goal and adding the fidelity `example`.
4. `lake build PastaBench` must pass, and `#print axioms` on a finished theorem should show only
   `propext, Classical.choice, Quot.sound`.

For which Python shapes stay provable, read
[`docs/verifiable-python-design.md`](../docs/verifiable-python-design.md) first — it is the
difference between a proof that closes in one line and one that cannot be stated at all.

## Provenance

Problems come from the [`newfacade/LeetCodeDataset`](https://huggingface.co/datasets/newfacade/LeetCodeDataset)
HuggingFace dataset (train split), normalized by `cp_harness/cpasta_eval.py`: the entry method is
extracted as a free function together with the helpers it reaches, and the test cases are the
dataset's own. `manifest.json` records the exact selection, seed, and source.
